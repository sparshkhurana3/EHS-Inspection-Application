# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An Environmental Health & Safety (EHS) inspection tool for a manufacturing company. An EHS Officer schedules weekly **patrols** (auditor + auditee + zone), the auditor submits an **observation report** holding up to 10 observations (a photograph each) or closes the audit with "no observation to record", the auditee works a **closure** (one action plan per observation, optionally with up to 3 photographs each as evidence the action was carried out), and the **EHS Officer approves the closure**, which completes the patrol. The auditee is responsible for carrying the action out: there is no ticket and no separate action team (`docs/19-remove-tickets-plan.md`). Two independent packages, no monorepo tooling:

- `backend/` — Express 5 + `pg` REST API (ES modules, no TypeScript, no test suite, no linter).
- `frontend/` — React 19 + Vite + react-router-dom v7 SPA. Plain CSS in `src/styles/global.css`. No state library.

`folder_structure.txt` at the root is stale (missing the `patrols` module, migrations 005/006, and lists an `init.sql` that doesn't exist). Don't trust it; use `find`.

**Knowledge base**: `docs/` holds the detailed reference (overview, architecture, data model, API, workflows, frontend, environment, containerization plan, refinement backlog). Start at [docs/README.md](docs/README.md). Keep this file short and link there.

**Current state**: the stack runs in Docker and the four workflows (plan, observe, close, approve) work end to end, including the weekly roster upload (`docs/14-weekly-roster-plan.md`): a one-time `.csv`/`.xlsx` upload schedules every zone for every upcoming Monday through 31 December, and the EHS Officer's dashboard shows a single upcoming-week card grouped by unit instead of the old per-unit cards. Migrations apply automatically on backend start. Microsoft Entra ID SSO is implemented (`docs/18-entra-sso-plan.md`) and is the primary authN/authZ source, with password sign-in kept as a failsafe; it stays dormant until a tenant is configured in `.env`. **`SETUP-GUIDE.md` at the repo root is the end-to-end on-premises deployment guide** (HTTPS, `.env`, master data, people import, SharePoint, Intune, backups); `guide.md` is its Entra chapter for the Microsoft 365 administrator. Keep both in step with the code. nginx serves **HTTPS only on 443** (certificate mounted from `certs/`, never committed), and photographs can be stored on the uploads volume or in **SharePoint via Microsoft Graph** (`PHOTO_STORAGE`). The action-ticket layer and the `ACTION_HOD` role were removed in migration 018 (`docs/19-remove-tickets-plan.md`). Remaining work is in `docs/09-feature-refinement-backlog.md`; the feature plans are `docs/10` to `19` and all are implemented.

## Commands

Install deps separately in each package (`npm install` in `backend/` and `frontend/`). There are no lockfile-level workspaces. **Host Node is v12**, which cannot run Express 5 or Vite 8; use Node ≥ 22 (nvm) or run in Docker (`docs/08-containerization-plan.md`). `backend/package.json` declares `"type": "module"`.

```bash
cp .env.example .env            # first run: set POSTGRES_PASSWORD and JWT_SECRET
docker compose up -d --build    # db + backend + frontend
docker compose logs -f backend
docker compose down             # add -v to also drop the data volume
```

App on https://localhost (nginx serves the SPA over HTTPS on 443 only and proxies `/api` to the backend, so the browser is same-origin). nginx will not start without `certs/tls.crt` and `certs/tls.key`; for a dev machine make a self-signed pair with the `openssl req` line in `SETUP-GUIDE.md` §3. Backend also published on 127.0.0.1:3000 for curl. Health check: `GET https://localhost/api/health` (or `http://127.0.0.1:3000/api/health`). `.env` changes need `docker compose up -d`; `restart` does not re-read it.

Operator commands run inside the backend container: `docker compose exec backend node scripts/admin.js help` (break-glass accounts, bulk `import-users`, `set-plant`, `deactivate-user`, `reassign-officer`; there are no admin screens) and `node scripts/sharepoint.js check|migrate`.

Migrations run automatically on backend start via `backend/scripts/migrate.js`, which records applied files in `schema_migrations`. Run them by hand with `npm run migrate` from `backend/`.

Host Node is v12 and cannot run this app; use the containers, or Node >= 22 via nvm. There are no tests and no linter.

### Database setup caveats

- `compose.yaml` mounts nothing into `docker-entrypoint-initdb.d`; the backend's migration runner builds the schema on first start.
- **The migrations build the full schema from empty and are idempotent** (verified 2026-09-19). `migrations/001` used to declare `users` with `first_name`/`last_name` while indexing `username`, which broke the chain at the first file; it now matches the deployed schema. To apply them by hand, in order:
  ```bash
  for f in backend/database/migrations/0*.sql; do
    docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < "$f"; done
  ```
  To get the existing data instead, restore `database-backups/ehs_full_dump.sql` and then apply 007 onward.
- Seeds in `backend/database/seeds/` create five test users (`test.auditor`, `test.auditee`, `test.ehs.officer`, `test.hod`, `test.plant.head`, password `ChangeMe123!`) plus sample patrols. Apply with `psql` the same way — **development only, never on a production database**. `001` currently fails at its `'REQUESTED'` closure status (line ~518; the CHECK wants `OPEN`) and creates no `zone_areas`. Migrations 007-010 are the ones to run on top of the dump. All migrations are idempotent.
- When changing schema, add a new numbered migration in `backend/database/migrations/`; keep it idempotent like the existing ones.

## Backend architecture

`src/app.js` wires middleware and mounts each module at `/api/<module>`. `src/server.js` verifies the DB connection then listens; startup fails fast if any required env var is missing (`config/environment.js` throws).

Every module in `src/modules/<name>/` follows the same five-file layering, and new endpoints should too:

| File | Role |
|---|---|
| `*.routes.js` | Express router: `authenticate` → `authorize(...roles)` → validation rules → `validate` → controller |
| `*.validator.js` | `express-validator` rule arrays (`body()`, `param()`, `query()`) |
| `*.controller.js` | Thin: pulls from `req`, calls service, `res.status().json()`, `next(error)` |
| `*.service.js` | All business rules; throws `AppError(message, status, CODE)`; uses `withTransaction` for multi-table writes |
| `*.repository.js` | Raw parameterised SQL via `databasePool` or a passed-in transaction `client`; maps `snake_case` rows → `camelCase` objects |

Cross-cutting pieces:

- **Errors**: always throw `shared/errors/AppError.js`. `middleware/errorHandler.js` serialises `{ message, code, details }`; 5xx messages are masked (unless the error sets `expose = true`, used for the user-facing `PHOTO_STORAGE_UNAVAILABLE`) and stacks only appear outside production. Validation failures become `VALIDATION_ERROR` with a `details: [{field, message}]` array that the frontend joins into one string.
- **Auth**: `middleware/authenticate.js` verifies a JWT (issuer `ehs-inspection-api`, audience `ehs-inspection-frontend`, `tokenType: "access"`) and re-loads the user from the DB on every request, so deactivated users are cut off immediately. `req.user.roles` is an array of role codes. `middleware/authorize.js` passes if *any* user role is in the allowed list. **Two ways in, one session**: password sign-in and Microsoft Entra ID SSO both end at `modules/auth/authSession.js`, which mints that JWT, so nothing downstream knows the difference. Never duplicate `createAccessToken`/`determineRedirectPath` — import them from there.
- **Entra ID SSO** (`docs/18-entra-sso-plan.md`, admin setup in `guide.md`): the primary authN/authZ source. Server-side OIDC authorization code flow with PKCE; the SPA never sees a Microsoft token, and the callback hands it a one-time code (`entra_login_sessions.exchange_code_hash`) which `POST /api/auth/entra/exchange` trades for the normal session envelope, so no token is ever put in a URL. **Entra app roles are authoritative**: every SSO sign-in rewrites `user_roles` from the `roles` claim, so a role withdrawn in the admin centre is gone at the next sign-in. Accounts are provisioned just in time. Entra is optional — with `ENTRA_TENANT_ID`/`ENTRA_CLIENT_ID`/`ENTRA_CLIENT_SECRET` unset the app runs on passwords only and the button is not drawn; setting *some* of the three fails at boot. **Password sign-in is the failsafe and is keyed on `password_hash` presence, not on `authentication_source`** — an account linked to Entra that started out local keeps both routes, and break-glass accounts are what make the failsafe real. **Self sign-up** (`SELF_SIGNUP_ENABLED`) is open while Entra is off and closes automatically once it is on (`SELF_SIGNUP_DISABLED` 403; `/api/auth/providers` reports `local.signupEnabled` and the pages hide their links); break-glass accounts are then made with `scripts/admin.js create-local-user`. The redirect URI defaults to `FRONTEND_ORIGIN` + `/api/auth/entra/callback`.
- **Roles** (`shared/constants/roles.js`): `USER`, `EHS_OFFICER`, `HOD`, `PLANT_HEAD`, `ADMIN`. Every signup gets `USER`, and an Entra sign-in gets whatever the directory says (`ENTRA_DEFAULT_ROLE`, default `USER`, when it says nothing). Seeds additionally insert `AUDITOR`/`AUDITEE` role rows but nothing in code checks them; auditor/auditee is a per-patrol relationship (`patrols.auditor_id` / `auditee_id`), not a role. Patrol planning endpoints require `EHS_OFFICER`; closure approval requires `MANAGEMENT_ROLES`; everything else requires `USER`. (`ACTION_HOD` and the `departments` table were dropped in migration 018 with the ticket system they served; accounts that held the role became ordinary `USER`s.)
- **Transactions**: `config/database.js` exports `withTransaction(async (client) => ...)`. Repository functions take an optional `client` as their last argument so they can run inside or outside a transaction.
- **File uploads**: `modules/observations/observationUpload.js` writes to `backend/uploads/observations/` (JPEG/PNG/SVG, 10 MB each, **up to 10 files**, field `photographs`, one per observation in the same order as the `observations` JSON field); `modules/closures/closureUpload.js` writes to `backend/uploads/closures/` (same types/size, field `evidence`, **up to 3 per observation** — the cap is per `closure_items` row, checked inside the transaction against a locked count, not by multer alone). Both relative to `process.cwd()`, so start the server from `backend/`. **What is stored is a compressed copy, never the camera original**: after `validate` and before the controller, `middleware/compressUploadedImages.js` re-encodes every JPEG/PNG with `sharp` (decoded once to a ≤2048 px sRGB raw buffer with EXIF orientation applied; JPEG quality 80; all metadata stripped including GPS; a PNG with real transparency stays PNG, any other PNG becomes the smaller of JPEG and PNG; SVG passes through untouched) and rewrites the multer record's `path`/`mimetype`/`size`/`originalname`, so the services store the compressed file without knowing. Guard rails: only the JPEG and PNG decoders may load (`sharp.block`), inputs over 120 MP are refused, and at most two compressions run at once per process. The 10 MB limit applies to what is sent, not what is stored. A file that will not decode is a 400 (`UNREADABLE_OBSERVATION_IMAGE` / `UNREADABLE_EVIDENCE_IMAGE`); a failure writing the result keeps its own error (500); either way every file in that request is deleted. `sharp` needs Node ≥ 20.9. **Storage**: with `PHOTO_STORAGE=sharepoint`, `middleware/storeUploadedFiles.js` then uploads each file to the configured library through `shared/storage/sharePointClient.js` (app-only Graph token, `Sites.Selected`) *before* the service's transaction and sets `file.path` to `sharepoint:<driveId>/<itemId>`, which is what the path columns store. Local paths and SharePoint references coexist; always remove or serve a stored file through `shared/storage/storedFiles.js` (`removeStoredFile(s)`, `sendStoredFile`), never with `unlink`/`res.sendFile` directly. `discardUploadsOnError` sits *before* each upload controller so a validation failure deletes the upload; it must never move after the controller, where it would delete files committed rows own. Files are served back through authenticated routes (`GET /api/observations/:reportId/photograph`, `GET /api/closures/:closureId/items/:closureItemId/evidence/:evidenceId`), never as static files. The service deletes the file(s) if the DB transaction fails, and on an evidence delete the row goes first and the file only after the commit. nginx's `client_max_body_size` is 110m to fit ten 10 MB observation photographs plus multipart overhead. `modules/patrols/rosterUpload.js` is the exception: it uses `multer.memoryStorage()` (`.csv`/`.xlsx`, 2 MB, field `roster`) because the file is parsed and discarded, never written to disk.
- **Logging**: `config/logger.js` prints one JSON object per line; morgan `combined` is added except in `NODE_ENV=test`.

### Domain workflow and status machines

The core lifecycle spans three tables and is driven by the observations and closures modules:

1. **Patrol** (`patrols.status`): `SCHEDULED` → `IN_PROGRESS` → `PENDING_AUDITEE_ACTION` → `PENDING_EHS_APPROVAL` → `REEXAMINATION_REQUIRED` / `COMPLETED`, or `CANCELLED`. Created either one at a time by `POST /api/patrols` (EHS Officer) or in bulk by `POST /api/patrols/roster` (a `.csv`/`.xlsx` upload that schedules every zone in it for every Monday from the upload date to 31 December; `patrols.roster_id` marks a roster-generated patrol, `NULL` for a hand-planned one — `docs/14-weekly-roster-plan.md`). The auditor and auditee of a zone must be different people (DB CHECK `patrol_auditor_auditee_check`), but one person may audit, or be audited on, any number of zones, including several on the same day. A patrol is located by a four-level cascade, Location → Unit → Zone → Area, where each zone has its own fixed area list (`docs/01-overview.md#location-hierarchy`). Level 4 is not modelled yet and the planning form cascades at no level.
2. **Observation report** (`observation_reports`, one per patrol, enforced by a unique index): `POST /api/observations` runs a single transaction that checks the patrol is assigned to the caller and is `SCHEDULED`/`IN_PROGRESS`, inserts the report **and its 1–10 `observation_items`** (one photograph each; the report's own per-observation columns stay filled with observation #1 so older queries keep working), **creates the `closure_requests` row** for the auditee, and moves the patrol to `PENDING_AUDITEE_ACTION`. `POST /api/observations/no-observation` is the other ending: it closes the audit with `no_observations = true`, no items and **no closure**, and completes the patrol. Reports are due by **Thursday of the audit's ISO week**; overdue ones are flagged, never blocked. `GET /api/observations/history?filter=` serves the last 6 months (`closed` means no observations were recorded, **or** the closure was approved — a report that can no longer come back to anybody). Categories are `UA`/`UC`; risk is `HIGH`/`MEDIUM`/`LOW`. Plant locations are currently a hardcoded list duplicated in the validator and a DB CHECK constraint, which violates R12 and is scheduled for removal.
3. **Closure** (`closure_requests.status`, migration 004): one closure per observation report, holding **one action plan per observation** in `closure_items` (migration 014), each with its own target date and up to three evidence photographs in `closure_item_evidence` (migration 018). The status is **derived** from those items by `closures/closureStatus.js` and rewritten whenever a plan is saved: `OPEN` while any observation lacks an action plan, `IN_PROGRESS` once every observation has one, then submittable (`POST /:closureId/submit`, requires `IN_PROGRESS`) → `SUBMITTED_FOR_CLOSURE` → `APPROVED` / `REEXAMINATION_REQUIRED`. **Evidence never gates the status**: it is optional supporting material, and the officer's approval is what decides whether it was enough. `closure_requests` keeps its own `action_plan`/`target_date` columns mirrored from item #1 so every older reader still works. Every item is editable for exactly as long as the closure is — nothing freezes one observation while the rest stay open. A rejection advances `approval_iteration` and reopens every observation for rework, keeping its existing plan text and photographs. Submission and approval both update the patrol and observation report in the same transaction. **The EHS Officer's approval of the closure is the only path that completes a patrol that had findings.** Full plan: `docs/19-remove-tickets-plan.md` (which supersedes the ticket half of `docs/16-closure-refinement-plan.md`).

`GET /api/patrols/inspection-report` builds the officer's **zone-by-week .xlsx** with `exceljs` (`patrols/inspectionReport.js`): one row per zone, one column per inspection week, green where the audit happened and red where it did not, plus the zone's configured areas (from `zone_areas`) and the auditor and auditee from that zone's most recent audit. Current year to today, scoped to the officer's plant, `PLANNING_ROLES` only. Colour *and* text carry the status so it survives black-and-white printing.

The dashboard also carries **year-to-date metrics** above the calendar, shaped by audience: management sees the plant's whole programme (inspections conducted vs scheduled so far, observation reports split by whether anything was found, closures approved vs raised), an ordinary user sees only their own, **split by the side of the patrol they were on** — conducted as auditor, closures completed as auditee — because merging them would credit an auditee with inspections somebody else carried out. The window is always the current year to today and does **not** follow the calendar's month/year navigation. Scoped to the viewer's plant (`users.plant_id`), or every plant when they have none.

"Current" assignment lookups (dashboard, observations, closures) are week-based: the observations repository computes ISO week numbers in SQL and the dashboard service computes week/month ranges in JS (`getCurrentWeekRange`, `getIsoWeekNumber`). Keep the two consistent if you change week semantics. The dashboard picks a *primary* role (management roles `EHS_OFFICER`/`HOD`/`PLANT_HEAD` get a plant-wide view, otherwise the user's own patrols) and accepts `?year=&month=`.

## Frontend architecture

- `src/app/App.jsx` → `BrowserRouter` → `AuthProvider` → `routes.jsx`. Public routes: `/`, `/sign-in`, `/sign-up`. Everything under `AppLayout` (`/dashboard`, `/observations`, `/closures`, `/plan`) redirects to `/sign-in` when unauthenticated. `/ehs-officer` (the backend's login redirect for EHS Officers) just forwards to `/dashboard`. Only `/plan` is role-gated, by `RequireRole roles={PLANNING_ROLES}`.
- **Auth state** lives in `localStorage` (`ehs_access_token`, `ehs_user`) and is mirrored into React context by `src/app/authProvider.jsx`. Use `useAuthenticatedUser()` to read `user`/`isAuthenticated`/`logout`. (`features/auth/useAuth.js` is the login/signup *form* hook and does not expose `user`, even though `Sidebar.jsx` currently destructures it from there.)
- **API calls** all go through `src/services/apiClient.js` (`apiRequest(endpoint, options)`), which attaches the Bearer token, sets JSON headers unless the body is `FormData`, and throws an `Error` carrying `status`/`code`/`details` from the backend envelope. The base URL is `import.meta.env.VITE_API_BASE_URL`, falling back to `/api`. `frontend/.env` sets it to `http://localhost:3000/api` for `npm run dev`; the container build passes `/api` as a build arg, which wins, so the browser is same-origin through nginx.
- Each feature folder under `src/features/<name>/` mirrors a backend module: `<name>.service.js` (thin `apiRequest` wrappers), `use<Name>.js` (a hook owning loading/error/success state, form state, and client-side validation that duplicates the backend rules), and page/components. Follow this split when adding a feature.
- Role helpers for the UI are in `src/constants/roles.js` (`hasManagementRole`, `normalizeRole`, `canPlanAudits`).

## Conventions worth keeping

- Backend and frontend both use a heavily line-broken formatting style (one argument per line, short lines). Match the surrounding file rather than reformatting.
- Response shapes are `{ message, ...data }` on success and `{ message, code, details }` on error. User-facing `message` strings are full sentences ending in a period; the frontend displays them verbatim.
- Repositories return `null` (not throw) when a row is missing; services turn that into a 404 `AppError`.
- **Location, unit, zone and area values must come from the database, never from code.** They are loaded into Postgres at production cutover, so a hardcoded list or a CHECK constraint would need a redeploy to accept a new site. Today they are hardcoded in ten places including three CHECK constraints; that is a known defect (R11/R12), not a pattern to copy. Read them through the planning lookups. See `docs/09-feature-refinement-backlog.md` item 2.0.
- Other allowed-value lists (`UA`/`UC`, `HIGH`/`MEDIUM`/`LOW`, the status enums) are fixed business vocabulary and do exist in validator, service, and a DB CHECK constraint. Change all three together with a migration.
